# FlowMuse 鸿蒙高校创新赛发展方向计划书

> 版本：v1.0  
> 日期：2026-08-20  
> 建议参赛方向：鸿蒙应用创新（以 AI 智能学习体验为核心）

## 1. 项目定位与本轮目标

### 1.1 一句话定位

**FlowMuse 是面向鸿蒙全场景学习的 AI 手写协作白板：把用户圈选的手写笔记、PDF 内容和语音指令，转化为可确认、可编辑、可协作的结构化学习成果。**

### 1.2 为什么选择“鸿蒙应用创新”

项目已经具备白板书写、PDF 批注、实时协作、AI 对话、语音输入和服务卡片等应用基础，最适合在现有底座上做一条完整、可感知的 AI 学习闭环。相比另起炉灶做系统协议或设备调度，本方向风险更低、可展示性更强，也更符合赛事对鸿蒙能力、AI 创意、完整性和应用价值的考查。

本轮不把 FlowMuse 扩展成题库、学习管理或通用聊天应用；只补齐它最关键的断点：**AI 目前能读文本，但不能直接理解用户正在书写和阅读的内容。**

### 1.3 最终演示场景

```text
学生在鸿蒙设备导入课程 PDF
  → 手写标注重点并圈选一段笔迹 / 当前 PDF 区域
  → 语音说“整理成三层知识导图”
  → AI 仅理解本次明确选中的内容
  → 展示来源、摘要和将写入白板的预览
  → 用户确认后生成普通文本或思维导图元素
  → 同伴实时看到结果并继续共同批注
  → 服务卡片显示“继续这块白板”入口
```

## 2. 当前基础与差距

| 能力 | 当前状态 | 本计划动作 |
|---|---|---|
| 自由书写、压感、形状、文本、撤销、导出 | 已有 | 保持稳定，不重写编辑器内核 |
| PDF 导入与批注 | 已有 | 新增“当前页/选区生成 AI 附件”入口 |
| 文本型 AI 助手与受限白板动作 | 已有 | 扩展为“文本 + 可视内容”上下文，保留确认机制 |
| 语音识别输入 | 已有 | 作为 AI 指令输入，补充状态、失败提示和演示脚本 |
| 加密协作与低延迟笔迹 | 已有 | 以稳定性回归测试为主，不新增协议 |
| 鸿蒙服务卡片 | 已有基础 | 从“最近白板”升级为“继续创作 + 本次学习状态” |
| PenKit | 已有颜色选择相关接入 | 优先验证并展示现有能力；预测点/智能形状仅作为后续增强 |
| AI 对手写、图片、PDF 的理解 | 缺失 | 本计划的核心新增能力 |
| 多设备接续、意图框架、端侧模型 | 未形成可验收闭环 | 不进入本轮主范围，作为后续路线 |

## 3. 产品方案：受控的“视觉语义学习闭环”

### 3.1 用户流程

1. 用户在白板中选择“选区 / 当前 PDF 页 / 图片”。
2. 客户端明确展示将发送的来源、页码或选区、图片数量和大小。
3. 用户选择任务：解释内容、提炼要点、生成思维导图、生成协作讨论提纲。
4. 语音或文字补充指令；语音只转写为同一输入框内容，用户可修改。
5. AI 返回文本或受限结构化动作，先显示预览，绝不直接改写白板。
6. 用户确认后，客户端生成普通白板文本 / 导图元素；撤销、保存、导出和协作沿用已有链路。

### 3.2 范围与边界

必须做到：

- 只上传用户主动选择的内容，不默认上传整块白板、整份 PDF 或协作房间内容。
- 每次最多 3 张视觉附件；单张压缩后不超过 4 MiB，限制最长边。
- 附件仅存在于当前 AI 请求内；不写入本地数据库、协作消息、导出文件或日志。
- AI 只能返回 `rename_note`、`insert_text`、`generate_mindmap` 等白名单动作；未知动作、超长文本和非法结构一律拒绝。
- 所有写入必须经过用户预览确认；网络失败时原白板内容不变。

明确不做：端侧大模型、长期记忆、向量数据库、任意模型写入画布、在线题库、跨端续接框架和新的协作协议。

### 3.3 鸿蒙特性选型与优先级

鸿蒙能力必须服务主闭环，并在真机上有可见、可复现的价值。以下优先级基于当前 Flutter + ArkTS 架构、已有原生通道，以及本次比赛的交付周期确定。

| 优先级 | 鸿蒙特性 | 在 FlowMuse 中的具体用法 | 实现边界与验收 |
|---|---|---|---|
| P0 | **Core Vision Kit 通用文字识别** | 将当前 PDF 页/图片选区先在设备侧 OCR 为文本，再作为 AI 上下文；用户可查看并修正 OCR 文本 | 新增 `OcrChannel`，输入只接受当前已选图片/PDF 位图；OCR 结果先预览、可编辑，绝不静默上传整份文档；固定 PDF 页识别成功并进入 AI 预览 |
| P0 | **PDF Kit** | 复用现有 PDF 导入，补“当前页转图、关键字高亮、书签/批注来源”能力，让 AI 结果能定位回原页 | 不修改原 PDF 文件；输出仅为临时位图、页码和选区元数据；能从 AI 预览回到正确页与区域 |
| P0 | **Form Kit 服务卡片** | 把现有“最近白板”卡片升级为“继续创作”：显示标题、最近更新时间、一个不含正文的学习状态和直达按钮 | 继续采用 ArkTS 常规卡片，不依赖互动卡片或云推送；卡片点击能路由到对应白板，卡片中不出现笔记正文、AI 内容或密钥 |
| P1 | **Core Speech Kit 文本转语音** | 对用户确认后的 AI 摘要提供“朗读”按钮，形成“手写—理解—听读”的无障碍学习体验 | 在已有语音识别通道旁增加 TTS 通道；仅朗读当前预览内容，用户可停止；真机完成一次朗读与停止 |
| P1 | **Pen Kit 全局取色** | 保留并强化已有取色能力，作为手写标注场景展示点 | 验证真实手写笔设备；失败时保留既有颜色面板降级 |
| P1（先做技术验证） | **Pen Kit 报点预测** | 仅为本地“湿墨预览”补预测点，减少笔尖与墨迹的视觉滞后 | Pen Kit 接口需要 ArkUI `TouchEvent`，而白板目前由 Flutter 接收指针事件；先完成原生事件/渲染桥接 Spike 并测量改善，再决定是否合入。预测点不得写入 Scene、可靠协作或最终笔迹 |
| P2 | **Pen Kit 一笔成形** | 用户停笔后将圆、矩形、箭头等草图转为现有白板形状元素 | 同样需要原生事件桥接；只作为现有形状工具的辅助，不允许自动替换，必须提供撤销 |
| P2 | **Intents Kit** | 暴露“打开最近白板”“搜索白板标题/标签”等系统入口能力，作为小艺搜索或语音入口的增强 | 需 HarmonyOS 5+、中国大陆及真机；仅共享标题、标签、更新时间等最小元数据，不共享正文、手写图像或协作信息 |
| 赛后 | **Agent Framework Kit** | 在小艺侧提供“继续整理当前学习白板”的入口 | 需要小艺开放平台上线智能体，且仅支持中国大陆 Phone/Tablet 真机；不把平台审核依赖放进比赛关键路径 |
| 不纳入本次 | **自由流转、Live View、Push 卡片刷新、代理提醒** | 未来可用于跨设备接续、专注计时或提醒 | 自由流转需要重构跨设备状态接续；实况窗/代理提醒有场景与权限限制；Push 卡片刷新需要服务端 Token 管理，均不应挤占主闭环交付 |

**关键技术决策：** Core Vision OCR 适合印刷体 PDF/图片，不宣称能够替代手写识别。手写选区仍优先走现有笔迹数据/识别能力，必要时由用户授权后以视觉附件交给兼容模型理解。这样既有端侧处理亮点，也不会夸大 OCR 能力。

## 4. 分阶段实施计划

### 阶段 A：冻结参赛叙事与体验契约（2 天）

**目标：先统一“做什么、证明什么、绝不做什么”，避免功能分散。**

| 任务 | 产物 | 验收条件 |
|---|---|---|
| 确定演示课程素材 | 1 份固定 PDF、3 段固定手写样例、1 份演示脚本 | 所有人使用同一素材可重放流程 |
| 冻结 AI 附件契约 | `AiVisualAttachment` 字段、大小限制、来源标签 | 前后端调用与 UI 文案一致 |
| 冻结白名单动作 | 动作 JSON schema、长度和层级上限 | 非法动作有自动化反例 |
| 设计隐私提示 | 选择前说明、请求中状态、失败与取消文案 | 用户能在发出前知道发送什么 |
| 确定赛事证据矩阵 | 功能—鸿蒙能力—截图/视频镜头映射表 | 每项能力都有可拍摄证据 |

### 阶段 B：AI 视觉附件 MVP（7 天）

**目标：完成“选中内容 → AI 可理解”的最小可用路径。**

| 子任务 | 实现要点 | 验收条件 |
|---|---|---|
| 选区采集 | 将用户选中的笔迹/文本区域按画布坐标渲染为 PNG | 坐标正确，不改变原场景 |
| PDF 页面采集 | 从当前 PDF 页或选区生成受限尺寸位图 | 页码、来源标签准确 |
| 图片输入复用 | 使用已有图片元素，不重新上传原始文件 | 可与笔迹/PDF 混合选择 |
| 压缩与限制 | 最多 3 张、单张 ≤4 MiB、超限给出可操作提示 | 超限不发网络请求 |
| AI 请求扩展 | OpenAI 兼容消息中附带视觉内容；纯文本路径不回归 | 文字与视觉两条请求均有测试 |
| 隐私与日志 | 请求体、API Key、图片字节均不写日志/持久化 | 日志扫描与单元测试通过 |

**建议技术原则：** 新增纯 Dart 数据模型和一个“附件构建器”即可；不要为单一模型供应商新增复杂抽象。模型不支持视觉时，明确提示并允许用户回到文字整理。

### 阶段 C：预览确认与白板落地（5 天）

**目标：AI 结果可靠地成为可编辑的白板内容。**

| 子任务 | 实现要点 | 验收条件 |
|---|---|---|
| 结果预览 | 显示来源、生成摘要、预计插入内容和操作类型 | 取消不会产生白板变更 |
| 内容校验 | 校验 JSON、最大文本、导图层级/节点数 | 恶意或格式错误回复被拦截 |
| 普通元素落地 | 客户端负责元素 ID、坐标、样式和批量提交 | 可撤销、保存、导出 |
| 协作兼容 | AI 结果走既有可靠场景更新；湿墨通道不承载 AI 结果 | 双人房间中结果一致 |
| 失败恢复 | 超时、模型拒绝、断网均保留用户原始内容与可重试输入 | 无崩溃、无半写入 |

### 阶段 D：鸿蒙体验收束（5 天）

**目标：让鸿蒙能力成为用户能看见的价值，而非代码清单。**

| 任务 | 用户可见价值 | 验收条件 |
|---|---|---|
| 服务卡片升级 | 显示最近白板标题、更新时间和“继续创作”入口 | 点击直达对应白板；无敏感正文 |
| 端侧 OCR 串联 | PDF 页/图片选区经 Core Vision OCR 后进入 AI 上下文 | OCR 文本可查看、编辑并可取消 |
| 语音 AI 指令与朗读 | 语音转写后可编辑，再执行 AI 请求；确认后的摘要可朗读 | 演示环境下可完成一次语音指令和一次停止朗读 |
| PDF + 手写串联 | 导入、批注、选区、生成导图全程连续 | 固定素材可在 3 分钟内完成，并可回到来源页 |
| 手写体验打磨 | 验证压感、全局取色、笔迹流畅度；报点预测仅在 Spike 通过后接入 | 真机连续书写无明显卡顿/跳变 |
| 可靠协作演示 | 两端看到 AI 确认后的结果与后续书写 | 固定网络条件下连续 5 次成功 |

> 此阶段应至少完成 3 项可见鸿蒙能力：PDF Kit、Core Vision OCR、Form Kit；语音与手写笔能力作为强化展示。跨设备接续、意图框架、预测点等功能若未完成，不应为了“能力数量”影响主闭环。

### 阶段 E：真机质量、参赛材料与提交（7 天）

| 任务 | 产物 | 验收条件 |
|---|---|---|
| 真机回归 | HarmonyOS HAP 安装包、设备测试记录 | 导入、书写、语音、AI、卡片、协作均通过 |
| 性能回归 | 书写/协作性能报告、关键日志脱敏检查 | 不出现明显性能回退或敏感信息 |
| 5 分钟视频 | MP4：痛点—流程—鸿蒙能力—价值 | 无剪辑也能完整复现核心闭环 |
| 作品说明 | 按官方模板的 PDF，控制在规定页数 | 创新、完整性、前景、规范均有证据 |
| 源码与 HAP 整理 | 可构建源码包、HAP、README、测试说明 | 第三方密钥和本地材料均未包含 |

## 5. 建议排期与里程碑

以 4 周为一个可控交付周期；每周结束必须有可运行版本，而不是只完成接口。

| 周期 | 里程碑 | 必须展示的结果 |
|---|---|---|
| 第 1 周 | 端侧素材与视觉附件 MVP | PDF/图片选区可经 OCR 或视觉附件获得 AI 文本回答 |
| 第 2 周 | 受控落地闭环 | AI 预览确认后生成可撤销的导图或文本 |
| 第 3 周 | 鸿蒙体验完成 | OCR、语音、PDF、服务卡片、双人协作串成演示 |
| 第 4 周 | 真机与材料封版 | HAP、视频、说明文档、回归记录齐全 |

每周固定保留半天处理缺陷和回归；未通过验收的功能不进入下一阶段。若赛程紧张，优先保证阶段 B、C、E，阶段 D 只保留服务卡片、语音和 PDF 演示。

## 6. 任务所有权与协作建议

| 角色 | 主责 | 不应同时改动的区域 |
|---|---|---|
| AI / 白板开发 | 附件构建、请求协议、结果校验、元素落地、测试 | 鸿蒙 ArkTS 卡片与原生通道 |
| 鸿蒙 / 体验开发 | 服务卡片、语音体验、PDF 真机链路、HAP 打包 | AI action schema 与白板核心写入 |
| 质量 / 材料负责人 | 固定素材、真机矩阵、视频、说明文档、提交清单 | 生产代码主干逻辑 |

共享变更仅限：附件模型、AI action schema、演示文案。它们应先评审、写测试，再并行开发。

## 7. 验收指标

### 功能指标

- 三种来源均可完成：手写选区、PDF 页面/选区、已有图片。
- 100% 的 AI 写入都经用户确认；取消后场景哈希不变。
- 非法模型动作、超限附件、断网和超时均无半写入。
- 双人协作下，确认后的文本/导图在两端一致。

### 质量与隐私指标

- 每次请求都显示来源与附件数量；默认不上传整块白板。
- API Key、附件字节、白板正文和协作密钥不进入日志、卡片或导出。
- 固定演示流程连续运行 5 次，无崩溃、无内容丢失。
- 每个新增核心路径至少有单元测试；端到端流程有真机录屏和手工验收表。

### 参赛表达指标

- 视频在前 30 秒讲清楚“手写/PDF 难以被普通 AI 理解”的痛点。
- 中段完整展示“圈选—理解—确认—落地—协作”。
- 结尾明确展示鸿蒙 PDF、语音、服务卡片和手写体验如何服务该闭环。
- 文档中的每一项“已实现”都有代码、真机截图或视频镜头佐证；规划项不冒充已完成。

## 8. 风险与降级策略

| 风险 | 处理策略 |
|---|---|
| 视觉模型不可用或成本不稳定 | 保留现有纯文本 AI 路径；比赛使用固定、已验证的兼容模型配置 |
| PDF/画布截图质量不足 | 先支持当前 PDF 页与矩形笔迹选区；不做复杂任意形状裁剪 |
| 模型输出不稳定 | 只接受受限 action；预览确认；客户端生成全部元素结构 |
| 真机适配拖延 | 第 1 周起每天在目标鸿蒙设备验证；不把真机集中到最后一周 |
| 功能范围膨胀 | 任何新点必须能强化主流程，否则列入赛后路线图 |

## 9. 赛后发展路线

主闭环稳定后，再按价值排序推进：

1. 通过意图框架或跨设备能力实现“从卡片/系统入口继续某个学习任务”。
2. 引入更完整的 PenKit 能力，如预测点与一笔成形，并用真机指标证明改善。
3. 研究端侧或私有化视觉模型，降低学习内容上传的隐私顾虑。
4. 在用户授权下建立可控的长期学习上下文；仍坚持“可查看、可删除、可关闭”。

这些项目不影响本次参赛闭环，只有在前述验收全部通过后才立项。

## 10. 决策结论

本次应把项目收敛为一个强而完整的能力：**让鸿蒙设备上的手写学习内容被 AI 在用户授权下理解，并安全地回到可编辑、可协作的白板中。**

它复用既有产品底座，新增范围有限，具有明确的用户价值、鸿蒙展示点和可验收标准；相比堆叠更多尚未验证的系统能力，更有利于在规定周期内交付有竞争力的作品。
