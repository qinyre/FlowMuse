## 已确认：陈旧摘要触发误补同步

位置：FlowMuse-App/lib/features/whiteboard/collaboration/repositories/collaboration_repository.dart 的 _receiveSyncStatus，约第 212—247 行。

当前实现把收到的哈希保存在定时器闭包中，600ms 后继续与本地现状比较。它没有再次确认对端的当前状态；在双向并发编辑中，收到的摘要可能对应已过期状态。

隔离复现：

1. 两端已有相同的 150 个元素。
2. 暂缓交付一份状态摘要。
3. 另一端修改 1 个元素，增量正常交付并合并，两端已经再次一致。
4. 交付迟到的旧摘要。
5. 接收端仍启动全量修复，额外发送 150 个元素。

实际观测：普通增量密文约 320 字节，额外全量约 38,844 字节。该例没有丢包，也不需要修复。诊断回执位于 FlowMuse-App/build/stale-status-regression-receipt.json。

复现命令（使用当前 Flutter 环境）：

    python build/create-stale-status-probe.py
    flutter test --no-pub build/stale_status_regression_probe_test.dart --plain-name "diagnostic stale status"

该诊断断言用于确认现状中的缺陷存在，不能将测试显示通过理解成修复完成。

## 已确认：大包拖慢实时墨迹

通过当前公网后端，用同一台电脑的两个隔离测试客户端，在同一 Socket.IO 连接上发送合成加密消息：

| 条件 | 实时帧延迟中位数 | 实时帧延迟 P95 | 最大延迟 |
| --- | ---: | ---: | ---: |
| 无大包，40 帧 | 26ms | 33ms | 44ms |
| 两端各发送约 395KB 的可靠包，并继续发送实时帧 | 422ms | 2186ms | 2495ms |

两次可靠确认分别耗时 166ms、1428ms；本次没有触发重试。1428ms 已接近当前 1500ms 确认超时，但不能把线上重复消息直接认定为重试。

采样窗口内，压力阶段提供 120 帧、本机接受发送 118 帧、接收 117 帧；这不是完整场景永久丢失率，实时通道本身允许丢帧。

回执：FlowMuse-App/build/live-under-bulk-diagnostic.json。
命令：

    flutter test --no-pub build/live_under_bulk_diagnostic_test.dart

这项实验不包含 Web 渲染和真实平板输入，因此不能把这些数值直接当作平板到 Web 的书写延迟。

## 线上脱敏观测与边界

- 当前后端运行正常，未重启循环，CPU 和内存没有明显饱和。
- 用户测试时出现约 330KB—429KB 的可靠消息；同一发送方的相同长度大包多次出现，相邻约 5—8 秒。
- 服务端密文长度日志不能证明消息具体类型、内容相同或是否为 ACK 重试。本次没有解密用户数据。
- 额外大小梯度实验中，约 395KB 的可靠消息本轮确认约 149—160ms，无重试；实际接收仍可能晚于确认。小包确认正常不能证明持续书写性能正常。

## 修复顺序

1. 先修正误补同步：迟到或短暂不一致的摘要不得直接触发整页重发；需要新鲜状态确认，并限制补偿发送频率。
2. 保持正式元素增量可靠发送，避免整页补偿反复占用实时连接。不要通过删除保存、墓碑或最终一致性逻辑掩盖问题。
3. 在相同服务器、相同合成历史场景下，分别比较九月默认配置、最新版关闭实验开关、最新版开启实验开关；测量持续书写、双向并发、加入与补偿期间的延迟和最终收敛。
4. 再检查远端湿墨渲染与实机开销。只有两端真实连续书写复测通过，才能说明体验恢复。

此前发布仅验证了启动、文件版本与孤立小包互通，没有覆盖大场景与实时帧争用，因此验证范围不足。
