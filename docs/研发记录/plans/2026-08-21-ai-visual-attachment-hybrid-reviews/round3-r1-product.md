## v3 新引入/残留问题

### [Important] R3-N1：满额 + 槽已占用时"不刷新"违背 1.2.2 自身的时效承诺，过期槽图随"解释这里"发送
- 证据：§1.2.2（L52）：先承诺"也保证'解释这里'解释的必是当前所见"，同句括号又规定"已满 3 张则提示……不自动驱逐、**不刷新**"——该满额条款未区分"槽空需新增"（计数 +1，确应受上限约束）与"槽已占用需替换"（移除旧槽+加入新槽，**计数中性**，不违反 ≤3 也不驱逐任何用户附件）。
- 问题：bar = [活动槽（旧选区 A）, PDF1, PDF2] 满额时，用户改选 B 后点"解释这里"：按现文不刷新 → 发送旧槽 A + "解释这里的内容"，恰是 1.2.2 承诺要杜绝的场景；同时提示语"移除一张以附带当前选区"与条内一张标签为"当前选区"的旧图并存，用户收到矛盾信号。规则句内部的承诺与满额条款自相矛盾，且计数中性的替换本可两全。
- 建议：满额条款改为"槽空且已满 3 张则提示'附件已满，移除一张以附带当前选区'，不自动驱逐；槽已占用时替换为计数中性操作，不受满额限制"。

### [Minor] R3-N2：「清除对话」清空附件时未声明同步清空活动槽引用
- 证据：§1.4（L66）"「清除对话」同时清空附件"；§1.1（L34）面板 State = `_attachments` + 活动槽引用；T6'（L124）"`_clearConversation` 清空附件"——三处均未提槽引用。
- 问题：槽引用悬垂指向已移除对象；后续快捷指令"替换活动槽附件"对不在条内的引用做移除，行为取决于实现者对悬垂引用的处理是否健壮。
- 建议：T6' 补一句"`_clearConversation` 同时清空活动槽引用"。

### [Minor] R3-N3：两条新"提示"的展示通道未指定，且满额/上限提示文案分叉
- 证据：§1.2 表（L44-46）对 StateError 明确"`_error` 展示"，但对两条非失败提示——满额提示"附件已满，移除一张以附带当前选区"（L52）与手动 chip null 提示"当前选区没有可截图的视觉内容"（L46/L83）——只写"提示"，未指明走 `_error` 容器还是附件条内联；另 §1.1（L31）添加 chips 达上限"禁用并提示"与 execution T6 的"最多添加 3 张图片"（`_addAttachment` 内）及 L52 满额提示是三处并存的上限文案。
- 问题：实现者可能一处用全局错误容器、一处用内联，视觉语义不一致（错误 vs 引导）；三处上限文案未统一收口。
- 建议：§1.2 表补"提示通道"一列（建议两条均走附件条内联的引导样式），上限类文案在 §1.6 或 §1.1 收口为一份。

### [Minor] R3-N4：手动选区截图与重建的活动槽并存时无去重规则，同选区可双份发送
- 证据：§1.2.3（L54）手动「选区截图」产物不登记槽；§1.2.2（L52）槽空时快捷指令无条件加入新槽——无"与既有附件同源去重"规则。
- 问题：用户移除自动槽 → 手动添加同选区截图 → 点"解释这里" → bar = [手动 S, 槽 S']（同一选区两张近似图）随请求发送，占用 2/3 配额；附件条可见可删，属可自愈的边缘态，但方案未声明。
- 建议：可在 T6' 注明"槽重建时若条内已存在同 kind 手动选区附件则跳过加入并提示"，或显式声明该重复态为接受行为。
