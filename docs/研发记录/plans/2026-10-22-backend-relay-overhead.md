# 后端转发开销审查与日志采样

## Context

用户反馈协作已明显改善，但仍有轻微卡顿，要求检查冗余进程和后端额外开销，并处理有证据的优化项。基线为已部署的 c8504b4 后端、应用及 main 合并提交 c48ca2a。

## 审查与范围

- 服务器只运行一份协作服务，另有 PostgreSQL、MinIO、Mailpit。2026-10-22 18:26 的短时采样 CPU 空闲 98%～99%、可用内存约 1015MiB、协作服务重启计数 0，未发现重复实例或明显资源争抢。短时低负载不代表覆盖书写高峰。
- 实时墨迹路径使用内存成员校验和限流，没有逐帧数据库查询；连接鉴权、加入房间和社交会话的定时鉴权保留既有安全语义。
- 实时帧的全局锁还保护成员退出与转发的先后关系，有并发回归测试约束。本轮不改变该边界。
- 普通可靠同步每个包都在转发前同步输出日志。大场景分批补偿会连续写出多条；复用已有 tokenBucket 对正常转发日志采样，按服务实例最多每秒一条，附累计帧数，不添加后台 goroutine。异常及实时丢帧诊断保持原有行为。
- 不改变消息格式、ACK、加密、房间权限、限流参数或客户端；不清理业务数据，不停止数据库、对象存储和系统服务。

## 验证及发布

先用固定时钟验证可靠日志有界、累计计数正确、实时帧不产生日志，并保留旧实现失败的证据；对比标准日志写入场景的基准与实际写入次数。执行 Go 全量测试和 vet，必要时使用 Linux race；发布前后以自建隔离房间验证真实加密补偿和实时帧互通。

确认仅服务端变更后只发布后端，保留旧镜像与回退配置、全部运行环境和数据。文档记录实测收益及边界，不将日志写入减少等同于真机帧率改善；若基准或回归不支持变更则保留审查结果，不发布该候选优化。

## 验证结果

- 新增测试在旧行为下失败：1000 个可靠转发写出 1000 条日志，并发发送也能突破采样预算；修复后同一时刻只输出一条。测试同时覆盖跨 20 个房间的并发调用、累计计数、1 秒补充预算和 volatile 帧不计入普通转发日志。
- `go test ./...`、`go vet ./...` 通过；`go test -race ./internal/collab -count=1` 通过（Windows/amd64，含真实 Socket.IO 回归）。没有改变退出房间与实时帧转发的互斥语义。
- `go test ./internal/collab -run '^$' -bench BenchmarkForwardLogging -benchmem -benchtime=200ms -count=3`：本机临时文件写入场景中，旧逐包诊断为 6898～6967ns/次、1 次分配；采样后的热点调用为 15.19～15.55ns/次、0 次分配。这仅测日志路径，不是整条转发或公网延迟，生产 stderr 的开销也可能不同。
- 发布前公网隔离双端仍能补回丢失元素，确认重试 0、50 个批次最大帧 16348 字节；本轮延迟 P95 基线 760ms、单项补偿 65ms、双向补偿 816ms（最大 2205ms），波动明显。不能用单轮前后差异证明服务器 CPU 或日志是剩余卡顿的主因。
- 本地证据：`FlowMuse-App/build/backend-relay-logging-before.log`、`backend-relay-go-test.log`、`backend-relay-race.log`、`backend-relay-log-benchmark.log`、`backend-relay-e2e-before.json`。
