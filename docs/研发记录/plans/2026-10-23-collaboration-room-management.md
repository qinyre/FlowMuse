# 协作房间人数与成员管理

## Context 与需求

Issue #66 的二维码入房已合并并部署，补齐创建人数上限和房主移出成员。复用现有房主账户/ownerKey 校验、在线成员列表和退出清理流程，保持笔画加密与转发热路径不变。

## 实现方案

- 人数按在线连接计算，包含房主，同一账号不同浏览器分别占位。默认不限，创建可选 2/4/8/16/32；服务端接受 0 或 2–50，0 表示不限。旧房间、旧请求缺字段继续不限。
- PostgreSQL 幂等增加 max_participants，创建重试不得修改既有房间设置。Socket.IO 入房在同一成员锁内检查和占位，重复入房不重复计数，离线释放名额。
- 房主通过现有独立 ownerKey 或认证账户授权，移出指定 socketId。仅针对本房间在线连接，不允许移出已验证的房主；撤销实时发送/接收资格并通知客户端停止重连。
- 移出不删除本地画布，不结束其他成员的房间，不做永久封禁。知晓邀请链接的用户仍可主动再次加入；不承诺撤回已下载的加密快照或密钥。
- 客户端增加创建上限选择、管理成员入口、移出确认、人数已满/已被移出的中文提示。只扩展房间元数据及管理事件，不改变 Scene、LWW、湿墨 V2 或加密消息格式。

## 关键文件与验证

RoomStore / HTTPAPI / Hub；EncryptedSceneStore / RealtimeTransport / CollaborationRepository；WhiteboardViewModel / WhiteboardPage 与现有协作菜单。

验证旧 schema 重复迁移、创建重试、非法上限、并发最后名额、重复入房、离开后再入、越权/跨房间/房主移出、被移出后广播和湿墨拒绝；验证客户端停止重连与本地画布保留、创建和管理交互。运行 Go test/vet、Flutter 全量测试及 analyze；构建与实际上线/真机验收分别记录。
