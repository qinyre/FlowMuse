# 应用运行期间的系统消息提醒

## Context 与范围

应用内提醒与列表选中态修复已推送至 PR #98。新功能分支为 `feature/system-message-notifications`，基于该 PR 的最新提交，待其合并后再核对主线。

用户最终确认本轮覆盖 Web、安卓、鸿蒙，先实现应用运行期间的系统通知，不建设关闭应用后的厂商推送。本轮不增加服务端进程、推送 SDK、前台常驻服务或新的后台轮询。系统暂停或结束应用/浏览器进程后，不承诺继续接收。

## 需求与实现方案

1. 默认关闭系统提醒，由用户在“好友与消息 → 消息提醒”主动申请系统授权；拒绝授权不影响原有消息功能。
2. 前台沿用应用内横幅；切到其他应用或浏览器标签页后，系统提醒开启时保留现有 `/social` 实时连接。免打扰同时暂停两类提醒；后台不增加定时补查。
3. 复用已有新消息、协作邀请、好友申请检测和历史基线；同一会话合并通知。正在前台查看的聊天不重复提醒，后台聊天不误判为已查看。
4. 通知预览开关同时控制横幅和系统通知。通知点击数据只包含当前账号、会话/申请标识及过期时间，不传账户令牌、房间密钥、白板内容或任意跳转地址。
5. 点击复用既有收件箱及白板保存/退出保护，禁止直接加入受邀房间。账号不匹配或通知过期时忽略。
6. 已读、屏蔽、邀请失效、免打扰、退出账号和关闭系统提醒时清除对应系统通知；异步权限与展示结果不得跨账号生效。
7. 原生采用小型 MethodChannel 适配系统通知 API；Web 采用仅通知用途的独立 Service Worker，不接管页面请求、不启用离线缓存或 Web Push。未支持的平台安全降级。

## 关键文件

- `FlowMuse-App/lib/features/social/`：通知模型、偏好、平台接口、提醒检测和消息连接生命周期。
- `FlowMuse-App/lib/app/`：平台适配装配、系统通知点击与既有收件箱衔接。
- `FlowMuse-App/android/`：Android 通知权限、通知通道、点击 Intent。
- `FlowMuse-App/ohos/entry/`：Notification Kit 权限、通知与 WantAgent。
- `FlowMuse-App/web/`：通知桥接脚本与仅通知用途的 Service Worker。

- 聚焦测试：后台接收与前台抑制、历史不重播、权限拒绝、关闭/DND/隐藏预览、已读取消、账号切换与异步竞争、点击保持白板保护。
- 检查 Web Service Worker 的作用域、来源检查、敏感信息隔离与点击安全。
- 运行改动文件静态检查、社交模块回归、Web 和安卓构建；涉及 Channel 按仓库要求尝试 HAP 构建。
- 当前鸿蒙 SDK 环境变量所指目录不存在；不得以代码静态检查代替 HAP 构建或真机结果。实机收到通知和点击行为另列为待验收。
