# 简化好友协作邀请

## Context 与需求

用户明确反馈：普通协作分享协作码即可，好友邀请不应要求双方交换安全卡。以本次要求取代 2026-09-23 计划中“安全卡双向核验是邀请前提”的交互约束。

## 方案与边界

- 登录且邀请功能可用后，应用在后台准备本机接收设备。普通流程为发送邀请 → 接受并加入白板，不要求打开设备管理或互换安全卡。
- 默认采用经 HTTPS、登录会话和好友关系鉴权的设备目录。沿用现有逐设备加密信封，不把协作码或明文 roomKey 写入云端私聊；房主、好友、撤销、到期、账号切换、AAD 与密钥校验保留。
- 手工安全卡核验保留为可选高级操作。默认目录可用不等于已经带外核验，不自动生成“已核验”标记；已有手工固定的同设备/同 keyId 公钥仍不得被静默替换。
- 默认模式信任服务端提供的公钥归属，不宣称能够防御恶意服务端首次替换公钥；独立身份核对须使用可选核验。此次不修改底层密码方案或协作协议。
- 尚未准备接收设备时提示好友打开应用并提供刷新；换设备收到旧邀请仍需补发，已有协作码入口保留。

## 关键文件与实施步骤

1. `invitation_device_store.dart` / `invitation_view_model.dart`：普通邀请使用目录设备，保持可选核验语义及错误边界；补免核验往返、拒绝无效设备与重试回归。
2. `flow_muse_app.dart`：通过账户作用域 Provider 自动准备设备，不阻塞其他功能；验证服务开关和账号生命周期。
3. 发送/接受邀请页面移除必经安全卡入口；设备安全文案明确“可选”；更新对应需求、原计划与服务说明。按逻辑与界面分别提交。

## 验证方案

- 双方没有信任记录也能发送、接受并还原房间密钥；网络重试幂等，不向请求泄露明文密钥；取消、账号切换、已核验公钥变化仍受约束。
- 邀请功能启用时自动登记；未启用、未登录不登记；发送窗口正常情况下只展示说明和发送按钮。
- 运行好友/邀请/协作加密测试、全量 Flutter 测试与 analyze；隔离后端联调与截图验证。
- 构建并发布 Web/Android，保留回滚版本；CI 通过后合并，鸿蒙真机交由队员验证。

## 创建成功后的邀请入口（增补）

用户要求在房间创建信息下增加“邀请好友”。在现有创建成功弹窗中增加该按钮，关闭信息弹窗后以模态打开现有好友列表；选择好友直接复用 `SocialInvitationHost` 的发送窗口，白板页面和房间保持存活。登录、空列表、服务关闭和房主权限继续沿用现有处理，不新增 API 或邀请协议。

验证创建成功到好友列表的跳转、选人发送入口及关闭列表后房间仍连接；检查窄屏弹窗可滚动，并运行相关测试、全量测试及静态检查，附界面截图。

增补验证完成：新增 3 项交互回归通过（390/1200 宽度直接选人、390×500 创建成功弹窗滚动及房间存活），全量 Flutter 测试 1770 项通过、6 项既有跳过；静态检查仍仅有上述本地忽略截图脚本的既有 warning。未改服务端、数据库或平台代码，鸿蒙真机仍由队员验收。
